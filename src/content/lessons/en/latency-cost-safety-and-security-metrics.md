data-lesson-section=""><span class="mr-2 tabular-nums font-normal text-muted-foreground">1<!-- -->.</span>Why one metric never certifies a Claude system</h2><p class="mt-4 leading-relaxed text-foreground">An evaluation metric is a number computed from a model's outputs on a test set and compared against a threshold. It tells you whether a prompt, model or configuration is ready to ship. You need it because "the model should classify sentiments well" can't be checked. "F1 of at least 0.85 on 10,000 held-out posts" can. The success criteria themselves are agreed during discovery (<a class="text-primary underline underline-offset-2 hover:no-underline" href="/en/lessons/writing-measurable-requirements-and-acceptance-tests-for-ai-solutions/">Measurable success criteria</a>). Here the job is the next step: turning each criterion into a formula that a script can compute on every run.</p><p class="mt-4 leading-relaxed text-foreground">Each metric is blind to some kind of failure. A classifier can label every ticket correctly and still take too long for a live chat. It can be fast and correct but cost more per ticket than the process it replaces. It can be fast, correct and cheap but answer in toxic language now and then. Or it can pass on every ordinary input and still leak details it was told to keep private. That is why the reference example of a good criterion is several thresholds on one held-out set, not one number: an F1 of at least 0.85, 99.5% non-toxic outputs, 90% of errors being an inconvenience rather than egregious, and 95% of responses under 200ms.</p><figure class="my-6"><figcaption class="mb-1.5 text-xs text-muted-foreground">The five metric dimensions, a computable form of each, and the failure that only that dimension catches</figcaption><div class="overflow-x-auto rounded-lg border border-border"><table class="min-w-full border-collapse text-sm"><thead><tr class="bg-muted/60"><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Dimension</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Computable metric with threshold</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Failure only this dimension catches</th></tr></thead><tbody><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Accuracy</td><td class="px-3 py-2 text-foreground">F1 score of at least 0.85 on a held-out test set; Even fuzzy goals like ethics and safety can be expressed as rates: the share of outputs, over a stated number of trials, that a stated detector flags. A good safety criterion names three things: the detector (a content filter), the sample size (10,000 trials) and the ceiling (fewer than 0.1% flagged). Severity needs the same treatment. "90% of errors would cause inconvenience, not egregious error" is computable only once you have written down what counts as inconvenient and what counts as egregious.</p><p class="mt-4 leading-relaxed text-foreground">A security metric is computed the same way. The difference is that you first have to define what counts as a successful attack, specifically enough that code or a grader can decide it. Start from the threat model, because there are two. In jailbreaks and direct prompt injection, the user is the adversary and writes inputs meant to get around your guardrails. In indirect prompt injection, the user is trusted, but Claude reads third-party content (web pages, emails, documents, tool results) that contains adversarial instructions. Each one needs its own adversarial test set and its own success condition. The metric is then the attack success rate: the share of attack attempts that meet that condition.</p><p class="mt-4 leading-relaxed text-foreground">Write success conditions as observable outcomes, never as "the model seemed manipulated":</p><ul class="mt-4 leading-relaxed text-foreground list-disc space-y-1 pl-6"><li class="pl-1">A harmlessness screen is a model call that labels incoming input as harmful or not before it reaches the main conversation. Structured outputs force it to return a fixed label, such as a boolean <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">is_harmful</code>, so code can compare it with the known answer. An attack succeeds when a known-harmful input comes back labelled safe.</li><li class="pl-1">For data handling, an attack succeeds when the output uses or shares a detail the instructions said to withhold.</li><li class="pl-1">For agents, an attack succeeds when the end state shows the forbidden effect, checked against environment state rather than the transcript's wording.</li></ul><p class="mt-4 leading-relaxed text-foreground">The authentication-bypass task below shows the agent version.
