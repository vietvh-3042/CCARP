Send the message to a lightweight model such as Claude Haiku 5.5 with a short classification prompt, and constrain the answer with structured outputs so it comes back as a value your code can branch on, not prose you have to interpret. A message flagged as harmful can then go to a stricter review flow and never reach the production model.</p><figure class="my-6"><figcaption class="mb-1.5 flex items-baseline justify-between gap-3"><span class="text-xs text-muted-foreground">The output_config that limits the screen's reply to a single boolean verdict</span><span class="shrink-0 rounded bg-muted px-1.5 py-0.5 font-mono text-[10px] uppercase tracking-wide text-muted-foreground">json</span></figcaption><pre class="overflow-x-auto rounded-lg border border-border bg-muted/50 p-4 text-[13px] leading-relaxed"><code class="font-mono text-foreground">{ <span class="text-primary">"output_config"</span>: { <span class="text-primary">"format"</span>: { <span class="text-primary">"type"</span>: <span class="text-emerald-700 dark:text-emerald-400">"json_schema"</span>, <span class="text-primary">"schema"</span>: { <span class="text-primary">"type"</span>: <span class="text-emerald-700 dark:text-emerald-400">"object"</span>, <span class="text-primary">"properties"</span>: { <span class="text-primary">"is_harmful"</span>: { <span class="text-primary">"type"</span>: <span class="text-emerald-700 dark:text-emerald-400">"boolean"</span> } }, <span class="text-primary">"required"</span>: [<span class="text-emerald-700 dark:text-emerald-400">"is_harmful"</span>], <span class="text-primary">"additionalProperties"</span>: <span class="text-amber-700 dark:text-amber-400">false</span> } } } }</code></pre></figure><p class="mt-4 leading-relaxed text-foreground">One case needs special handling. Claude Haiku 5.5 runs its own safety classifiers, so a really harmful message can make the screening call itself decline. That reply has no <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">is_harmful</code> field to read. Treat <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">stop_reason: "refusal"</code> from the screen as a harmful verdict, not as a failed call to retry or wave through.</p><p class="mt-4 leading-relaxed text-foreground">The tempting alternatives all miss part of the requirement. Asking the production model to classify the message as well as answer it pays production-model prices twice, and the message has already reached the main conversation. Reading refusal text out of the main model's final reply comes too late to be a pre-screen. A fixed keyword blocklist is a valid <strong class="font-semibold">input validation</strong> layer, but it is one layer, not the last check. An LLM given known jailbreak language as examples acts as a generalized validation screen that catches reworded attempts a literal match would miss.<!-- --></p><p class="mt-4 leading-relaxed text-foreground">The system prompt is the second layer. State the values the assistant must uphold, such as integrity, compliance, privacy and respect for intellectual property, and spell out exactly what Claude should say when a request conflicts with them, for example "I cannot perform that action as it goes against AcmeCorp's values." A fixed refusal sentence makes refusals predictable for users and easy to detect in logs.</p><p class="mt-4 leading-relaxed text-foreground">Output checks catch what slips past the input side. Post-process Claude's replies with regular expressions or keyword filters for content that must never appear, such as a proprietary formula from your prompt. Keep that protection proportionate: piling leak-prevention instructions into the prompt adds complexity that can degrade the task itself, and the most effective step is often to leave out details Claude does not need.</p><p class="mt-4 leading-relaxed text-foreground">Persistent attackers show up in the logs as a pattern: the same account triggering the same kind of refusal again and again with slightly reworded prompts. Respond to those accounts specifically. Tell the user that their actions violate the relevant usage policies, then throttle or ban as warranted.
