authenticates</h2><p class="mt-4 leading-relaxed text-foreground">Reviewing authentication for an MCP integration starts with one question: how does the client reach the server? A server reached over HTTP is a network service. Anyone who can reach its URL can send it requests, so it needs real authorization, and the MCP authorization specification is built on OAuth 2.1. A server launched locally over STDIO is a child process of the client. leading-relaxed text-foreground">The client does not need to know in advance where to get a token. Discovery begins with an unauthenticated request. The MCP server replies <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">401 Unauthorized</code> with a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">WWW-Authenticate</code> header, and that header carries a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">resource_metadata</code> URL pointing to the server's OAuth 2.0 Protected Resource Metadata document. Every MCP server must publish this document, and clients must use it to find the authorization server. It can be served at a well-known URI, either at the root (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">/.well-known/oauth-protected-resource</code>) or with the MCP endpoint's path appended.</p><figure class="my-6"><figcaption class="mb-1.5 flex items-baseline justify-between gap-3"><span class="text-xs text-muted-foreground">The 401 challenge that starts discovery: a pointer to the metadata document plus a scope hint</span><span class="shrink-0 rounded bg-muted px-1.5 py-0.5 font-mono text-[10px] uppercase tracking-wide text-muted-foreground">http</span></figcaption><pre class="overflow-x-auto rounded-lg border border-border bg-muted/50 p-4 text-[13px] leading-relaxed"><code class="font-mono text-foreground">HTTP/<span class="text-amber-700 dark:text-amber-400">1.1</span> <span class="text-amber-700 dark:text-amber-400">401</span> Unauthorized&#10;WWW-Authenticate: Bearer resource_metadata=<span class="text-emerald-700 dark:text-emerald-400">"https://mcp.example.com/.well-known/oauth-protected-resource"</span>,&#10;                         scope=<span class="text-emerald-700 dark:text-emerald-400">"files:read"</span></code></pre></figure><p class="mt-4 leading-relaxed text-foreground">Next, the client fetches the authorization server's own metadata. The authorization server must offer at least one of OAuth 2.0 Authorization Server Metadata (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">/.well-known/oauth-authorization-server</code>) or OpenID Connect Discovery (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">/.well-known/openid-configuration</code>), and the client must support both. If the metadata has no <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">code_challenge_methods_supported</code> field, the client must stop. A missing field means the server does not support PKCE, and the client must not proceed without it.<!-- --></p><p class="mt-4 leading-relaxed text-foreground">These are the transport rules to check in an audit. Every authorization server endpoint must be served over HTTPS. Every redirect URI must be either localhost or HTTPS. The specification sets an order of preference:</p><ol class="mt-4 leading-relaxed text-foreground list-decimal space-y-1 pl-6"><li class="pl-1">Use pre-registered client information, if the client and server already have a relationship.</li><li class="pl-1">Use a Client ID Metadata Document, if the authorization server advertises <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">client_id_metadata_document_supported</code>. This is the usual case when the two have no prior relationship.</li><li class="pl-1">Fall back to Dynamic Client Registration, if the server publishes a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">registration_endpoint</code>.</li><li class="pl-1">Otherwise, ask the user to enter client details.</li></ol><p class="mt-4 leading-relaxed text-foreground">With a Client ID Metadata Document, the client's <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">client_id</code> is itself an HTTPS URL with a path component. The JSON hosted at that URL must include <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">client_id</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">client_name</code> and <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">redirect_uris</code>, and its <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">client_id</code> must match the document URL exactly.  <span class="text-primary">"client_uri"</span>: <span class="text-emerald-700 dark:text-emerald-400">"https://app.example.com"</span>,&#10;  <span class="text-primary">"logo_uri"</span>: <span class="text-emerald-700 dark:text-emerald-400">"https://app.example.com/logo.png"</span>,&#10; An attacker can present the legitimate client's metadata URL as their own <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">client_id</code> and bind to a localhost port listed in its redirect URIs. When the user approves, the attacker's listener receives the authorization code. The specification responds on the consent screen.
