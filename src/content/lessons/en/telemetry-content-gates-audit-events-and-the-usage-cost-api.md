The session object's <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">usage</code> field holds cumulative token counts, cache reads and writes, server tool requests, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">active_seconds</code> and <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">list_cost</code>. A session can run several threads, for example one per agent in a multiagent session, and the Console's session viewer shows one timeline lane per thread, a transcript, and a Tools tab with failure counts and median duration. <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">active_seconds</code> is the time during which at least one thread was running, with overlapping threads counted once. The session's running-time cost is priced on that duration. Each thread also reports its own <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">list_cost</code>, but per-thread costs are rounded independently and leave out the running-time cost, so the session figure is the authoritative one.</p><p class="mt-4 leading-relaxed text-foreground">A <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">session.usage</code> event carries the same cumulative snapshot on the session stream, so you don't have to poll. It is emitted on idle transitions rather than on a timer: immediately before the session goes idle, and when a thread pauses at a session budget. During a long run you therefore see no new totals until one of those moments. That is why a spend cap built from watching usage and stopping the session yourself fails, since the stop arrives after the money is spent. A session budget is a dollar cap on list cost.
