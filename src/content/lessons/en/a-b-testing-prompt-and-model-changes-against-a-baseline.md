class="scroll-mt-20 text-xl font-semibold leading-snug text-foreground" data-lesson-section=""><span class="mr-2 tabular-nums font-normal text-muted-foreground">1<!-- -->.</span>Baselines and targets come before the change</h2><p class="mt-4 leading-relaxed text-foreground">Iterative improvement is a loop: change one thing, measure it against what you already have, then keep the change or drop it. The "what you already have" is the <strong class="font-semibold">baseline</strong>, which is usually the prompt, model or configuration serving production today. A candidate counts as better only when it beats that baseline on the criterion you set in advance. Feeling better to the person who wrote it doesn't count. Anthropic's guidance lists A/B testing among the quantitative methods for exactly this: comparing performance against a baseline model or an earlier version.</p><p class="mt-4 leading-relaxed text-foreground">A target turns the comparison into a decision. The sentiment-classification example in Anthropic's success-criteria guidance does not stop at "F1 of at least 0.85". It also says that this figure is a 5% improvement over the current baseline. Each target is anchored to something real: industry benchmarks, prior experiments, AI research or expert knowledge. A prior experiment is itself a baseline. Setting the bar before you run the comparison stops you from moving it once the numbers come in. Choosing which metrics to track is its own skill, covered under <a class="text-primary underline underline-offset-2 hover:no-underline" href="/en/lessons/latency-cost-safety-and-security-metrics/">defining evaluation metrics</a>. Here the point is that every metric you iterate on needs both a starting value and a finish line.</p><p class="mt-4 leading-relaxed text-foreground">Baselines get cheaper once you have them. An eval suite run against the production version records latency, token usage, cost per task and error rates on a fixed bank of tasks. Every later candidate is scored against that record. id="section-2" class="scroll-mt-20 text-xl font-semibold leading-snug text-foreground" data-lesson-section=""><span class="mr-2 tabular-nums font-normal text-muted-foreground">2<!-- -->.</span>Offline comparisons on a held-out eval set</h2><p class="mt-4 leading-relaxed text-foreground">The fastest fair comparison is offline. Run the baseline and the candidate over the <strong class="font-semibold">same held-out, labelled set</strong> and score both with the same grader. Real users are never exposed to the candidate, the run can be repeated, and it finishes in minutes. Building that set belongs to <a class="text-primary underline underline-offset-2 hover:no-underline" href="/en/lessons/evaluation-datasets-test-cases-edge-cases-and-volume/">evaluation dataset design</a>. For the comparison, two things matter: which grader you use and how many cases you have.</p><p class="mt-4 leading-relaxed text-foreground">Pick the most objective grader the task allows. A ticket classifier that outputs urgent, normal or low has a clear-cut categorical answer, so <strong class="font-semibold">exact match</strong> against human-labelled ground truth is the right score. It checks whether the output equals the predefined correct label, usually after normalising whitespace and case. Asking Claude to rate its own confidence in each label does not do this, because confidence is not correctness and nothing is checked against the labels. Having two colleagues read samples and vote on which version "feels" more accurate is slower and less objective than a score both versions earn on the same answers.</p><p class="mt-4 leading-relaxed text-foreground">Open-ended output needs a different score. When a summarisation prompt is compared against human-written reference summaries, exact string match fails almost every case, because two good summaries rarely share wording. <strong class="font-semibold">ROUGE-L</strong> scores a candidate by the longest common subsequence it shares with the reference. A summary that keeps the reference's key information in a similar order scores high, and the F1 can be tracked across prompt variants at scale. Latency is a separate, operational criterion: a faster variant has not shown that its summaries are better.</p><figure class="my-6"><figcaption class="mb-1.5 text-xs text-muted-foreground">Matching the comparison score to the task</figcaption><div class="overflow-x-auto rounded-lg border border-border"><table class="min-w-full border-collapse text-sm"><thead><tr class="bg-muted/60"><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Task output</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Score to compare variants on</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Why<!-- --></th></tr></thead><tbody><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Categorical label (sentiment, ticket priority)</td><td class="px-3 py-2 text-foreground">Exact match against human-labelled answers</td><td class="px-3 py-2 text-foreground">Unambiguous and cheap to re-run on every candidate</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Free-text summary with a reference summary</td><td class="px-3 py-2 text-foreground">ROUGE-L F1 against the reference</td><td class="px-3 py-2 text-foreground">Rewards keeping the reference's key information in order, which exact match cannot</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Response speed</td><td class="px-3 py-2 text-foreground">Response time (ms)</td><td class="px-3 py-2 text-foreground">An operational criterion, tracked alongside quality rather than in place of it</td></tr></tbody></table></div></figure><p class="mt-4 leading-relaxed text-foreground">Volume beats hand-polished quality. Anthropic's rule is that more questions with slightly lower-signal automated grading are better than fewer high-quality, hand-graded ones. The reason is economic. Writing questions is mostly a one-time cost, but grading is paid every time the eval is re-run, and iteration means re-running it constantly. Eighty carefully hand-labelled cases that someone must re-grade by hand after every prompt edit will slow you down. An automatically graded set of several hundred cases gives the same comparison every time you run it, at no extra effort.</p><aside aria-label="Exam traps" class="my-6"><p class="flex items-center gap-1.5 text-xs font-semibold uppercase tracking-wide text-amber-700 dark:text-amber-400"><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-triangle-alert h-3.5 w-3.5 shrink-0" aria-hidden="true"><path d="m21.73 18-8-14a2 2 0 0 0-3.48 0l-8 14A2 2 0 0 0 4 21h16a2 2 0 0 0 1.73-3"></path><path d="M12 9v4"></path><path d="M12 17h.01"></path></svg>Exam traps</p><ol class="mt-3 space-y-3"><li id="exam-trap-1" class="scroll-mt-20"><details class="group rounded-lg border border-border bg-muted/20 p-4 open:bg-muted/40"><summary class="cursor-pointer list-none"><span class="flex items-start gap-2"><span class="min-w-0 text-sm font-medium leading-relaxed text-foreground [overflow-wrap:anywhere]">A prompt version whose outputs Claude rates with higher average confidence is the more accurate version.</span></span><span class="mt-1.5 block text-xs text-primary group-open:hidden ">Why is that wrong?</span></summary><p data-explanation="exam-trap-1" class="mt-2 text-sm leading-relaxed text-foreground">Self-reported confidence is not a correctness score.
