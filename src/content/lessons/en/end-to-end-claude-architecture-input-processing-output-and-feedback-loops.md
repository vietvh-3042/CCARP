text-foreground" data-lesson-section=""><span class="mr-2 tabular-nums font-normal text-muted-foreground">1<!-- -->.</span>The agent loop from input to output</h2><p class="mt-4 leading-relaxed text-foreground">Every Claude-based architecture, from a single tool call to a multi-hour coding agent, runs the same cycle. Draw that cycle first and the rest of the design hangs off it: where the input comes from, what runs during processing, what counts as output, and where feedback comes back in.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Input</strong> is more than the user's message. Each time Claude is called it sees the prompt, the system prompt, the tool definitions and the conversation history so far. So the design decisions that shape every turn sit here: which tools to expose, what instructions to give, how much history to carry. The Agent SDK marks the start of a run with a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">SystemMessage</code> of subtype <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">init</code>, which carries the session metadata.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Processing</strong> happens in turns. Claude looks at the current state and replies with text, one or more tool calls, or both. The tools run, and each set of results goes back to Claude for its next decision. One full pass of evaluate-then-execute is a turn, and an agent may take many turns before it finishes.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Output</strong> comes when Claude gives a response that contains no tool calls. In the Agent SDK that final text arrives as an <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">AssistantMessage</code>, followed by a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">ResultMessage</code> that holds the final text, token usage, cost and session ID. Check the <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">ResultMessage</code> subtype as well, because a run can end by hitting a limit rather than by succeeding.</p><p class="mt-4 leading-relaxed text-foreground">A worked case shows the shape. The task is to fix a failing auth test. In turn 1 Claude runs <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">npm test</code> through Bash and gets back three failures. In turn 2 it reads <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">auth.ts</code> and <!-- --><code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">auth.test.ts</code>. In turn 3 it edits <!-- --><code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">auth.ts</code> and runs the tests again, and all three pass. The final turn has no tool call, only the text "Fixed the auth bug, all three tests pass now." Nobody coded those steps in advance. Claude chose each one based on the result of the step before.<!-- --></p><p class="mt-4 leading-relaxed text-foreground">With the raw Messages API you write this loop yourself. It is a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">while</code> loop keyed on <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">stop_reason</code>: if the reason is <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">tool_use</code>, run the requested tools, add the <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">tool_result</code> blocks to the conversation and send it again. Any other stop reason ends the loop, and your application has to handle each one.</p><figure class="my-6"><figcaption class="mb-1.5 text-xs text-muted-foreground">What the application does for each stop_reason</figcaption><div class="overflow-x-auto rounded-lg border border-border"><table class="min-w-full border-collapse text-sm"><thead><tr class="bg-muted/60"><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">stop_reason</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">What it means</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">What your code does next</th></tr></thead><tbody><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">tool_use</td><td class="px-3 py-2 text-foreground">Claude wants one or more tools run</td><td class="px-3 py-2 text-foreground">Run them, send tool_result blocks, call again</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">end_turn</td><td class="px-3 py-2 text-foreground">Claude produced its final answer</td><td class="px-3 py-2 text-foreground">Leave the loop and deliver the output</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">max_tokens, stop_sequence, refusal</td><td class="px-3 py-2 text-foreground">Claude stopped for some other reason</td><td class="px-3 py-2 text-foreground">Leave the loop and handle that case explicitly</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">pause_turn</td><td class="px-3 py-2 text-foreground">A server-side tool loop hit its iteration cap with work still to do</td><td class="px-3 py-2 text-foreground">Send the conversation again, including the paused response</td></tr></tbody></table></div></figure><p class="mt-4 leading-relaxed text-foreground">You also have to decide who hosts the loop. itself. It emits a structured request, something outside the model carries it out, and the result goes back into the conversation. The main design question for any tool is therefore where its code runs, because that decides what your application is responsible for.</p><aside class="my-6 rounded-lg border-l-4 border-l-amber-500/70 border-y border-r border-border bg-amber-500/5 p-4 dark:border-l-amber-400/60 practice-question predict-first" data-practice-id="predict-1"><p class="flex items-center gap-1.5 text-xs font-semibold uppercase tracking-wide text-amber-700 dark:text-amber-400"><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-lightbulb h-3.5 w-3.5 shrink-0" aria-hidden="true"><path d="M15 14c.2-1 .7-1.7 1.5-2.5 1-.9 1.5-2.2 1.5-3.5A6 6 0 0 0 6 8c0 1 .2 2.2 1.5 3.5.7.7 1.3 1.5 1.5 2.5"></path><path d="M9 18h6"></path><path d="M10 22h4"></path></svg>Predict first</p><p class="mt-1.5 text-sm leading-relaxed text-foreground">Anthropic publishes the schema for the <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">bash</code> tool. You write the schema, run the code and return the result. Claude sees the schema and the result but never your implementation. <strong class="font-semibold">Anthropic-schema client tools</strong> (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">memory</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">bash</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">text_editor</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">computer</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">browser</code>) run the same way, in your code. The difference is that Claude was trained on these exact signatures, so it calls them more reliably and recovers from errors better than it would with a custom tool that does the same job. <strong class="font-semibold">Server tools</strong> (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">web_search</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">web_fetch</code>, <!-- --><code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">code_execution</code>, <!-- --><code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">tool_search</code>) run on Anthropic's infrastructure. You enable them in the request and never build a <!-- --><code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">tool_result</code> for them.<!-- --></p><figure class="my-6"><figcaption class="mb-1.5 text-xs text-muted-foreground">Where each kind of tool sits in the architecture</figcaption><div class="overflow-x-auto rounded-lg border border-border"><table class="min-w-full border-collapse text-sm"><thead><tr class="bg-muted/60"><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Tool kind</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Who executes</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Your loop's job</th></tr></thead><tbody><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">User-defined client tool</td><td class="px-3 py-2 text-foreground">Your application</td><td class="px-3 py-2 text-foreground">Run the operation, return tool_result, drive the loop</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Anthropic-schema client tool (bash, text_editor, computer…)</td><td class="px-3 py-2 text-foreground">Your application</td><td class="px-3 py-2 text-foreground">Same as above; Claude calls it more reliably because the schema is trained-in</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Server tool (web_search, web_fetch, code_execution, tool_search)</td><td class="px-3 py-2 text-foreground">Anthropic</td><td class="px-3 py-2 text-foreground">Enable it and read the results; resend on pause_turn</td></tr></tbody></table></div></figure><p class="mt-4 leading-relaxed text-foreground">Client tools put a round trip in every call. The model can't run your code, so it asks, you execute, you report back, and it carries on. Server tools turn that around. A single request can set off several searches or code runs inside Anthropic's own loop, and the response arrives with the <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">server_tool_use</code> blocks already done. Your application usually just reads the answer.</p><p class="mt-4 leading-relaxed text-foreground">That server-side loop has two exits to design for. It has an iteration cap, and hitting the cap returns <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">pause_turn</code> instead of <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">end_turn</code>. A tool that only says "done" gives it nothing to correct against.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Hooks</strong> turn feedback into code that runs every time, whatever the model decides. The Agent SDK lets hooks intercept, modify or block a tool call before it runs (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">PreToolUse</code>), and fire after a tool has run (<code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">PostToolUse</code>). Each <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">HookMatcher</code> pairs a matcher pattern such as <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">Write|Edit</code> with a list of callbacks. To write an audit entry every time the agent changes a file, register a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">PostToolUse</code> hook matched to <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">Edit|Write</code> whose callback appends the entry. Putting "remember to log your edits" in the system prompt depends on the model complying on every turn of a multi-hour run. Polling the filesystem from outside only guesses at what changed. Asking the user to confirm each edit is a human approval gate, not an audit log.</p><figure class="my-6"><figcaption class="mb-1.5 flex items-baseline justify-between gap-3"><span class="text-xs text-muted-foreground">Agent SDK (Python): hook callbacks registered through HookMatcher;
