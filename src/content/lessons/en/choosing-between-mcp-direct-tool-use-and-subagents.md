font-normal text-muted-foreground">1<!-- -->.</span>Three ways to connect Claude to a system</h2><p class="mt-4 leading-relaxed text-foreground">Each time Claude needs to reach an outside system, such as a database, an issue tracker or a build server, the architect picks one of three mechanisms: a tool your application defines and runs, an MCP server, or another agent that owns that system. All three can get the job done. They differ in who maintains the integration, how many clients can reuse it, and how much judgement sits on the other side.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Direct tool use</strong> is the shortest path. Your application defines a tool with an <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">input_schema</code>, Claude returns a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">tool_use</code> block, your code runs the operation and returns a <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">tool_result</code>. Where that code runs is covered in <a class="text-primary underline underline-offset-2 hover:no-underline" href="/en/lessons/end-to-end-claude-architecture-input-processing-output-and-feedback-loops/">Who executes tools: client tools versus server tools</a>. As an integration choice, it wins when one application owns one system and you control the schema. A CLI belongs here too: Anthropic publishes a bash tool schema, but your application still runs each command. The cost is that this integration lives inside your application. A second client, say a developer's Claude Code session, cannot reuse it.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">An MCP server</strong> moves the integration out of your application and puts it behind a protocol. One server can then serve any MCP client, and one client can combine several servers. Each server sees only what it needs, because the full conversation stays with the host. MCP wins when the same capability has to be reachable from more than one surface, or when the vendor of the system already ships an MCP server you can attach rather than build.</p><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Agent-to-agent</strong> hand-off is the right choice when the system needs its own judgement, not just a function call: a security review, a test-writing pass, a domain specialist with its own system prompt and toolset. The calling agent delegates the task and reads back what the specialist reports, instead of driving each step itself. How subagents, agent teams and workflows differ is taught in <a class="text-primary underline underline-offset-2 hover:no-underline" href="/en/lessons/multi-agent-system-design-when-to-split-and-how-to-decompose/">Subagents vs agent teams vs workflows across Managed Agents, Agent SDK and Claude Code</a>.<!-- --></p><p class="mt-4 leading-relaxed text-foreground">In Managed Agents the specialist is either a predefined agent listed in the <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">multiagent</code> block of the lead's definition, or an inline agent that the lead defines when it delegates. Each subagent works in its own session thread, so its working context stays out of the lead's. Delegation is one level deep: a specialist cannot hand work on to further agents. Pick this over a tool or an MCP server when the system must reason about the task, and expect the lead to receive a report rather than a raw result.</p><figure class="my-6"><figcaption class="mb-1.5 primitives and transports</h2><p class="mt-4 leading-relaxed text-foreground">MCP standardises three kinds of things a server can expose, and each one is controlled by a different party. That split matters when you compare MCP with a plain tool definition, because a tool definition only covers the first row of the table below. Resources and prompts give a client context and templates that it, or the user, chooses to bring in.</p><figure class="my-6"><figcaption class="mb-1.5 text-xs text-muted-foreground">MCP server primitives and who controls them</figcaption><div class="overflow-x-auto rounded-lg border border-border"><table class="min-w-full border-collapse text-sm"><thead><tr class="bg-muted/60"><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Primitive</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Control</th><th scope="col" class="px-3 py-2 text-left align-bottom font-semibold text-foreground">Example</th></tr></thead><tbody><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Tools</td><td class="px-3 py-2 text-foreground">Model-controlled</td><td class="px-3 py-2 text-foreground">API POST requests, file writing</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Resources</td><td class="px-3 py-2 text-foreground">Application-controlled</td><td class="px-3 py-2 text-foreground">File contents, git history</td></tr><tr class="border-t border-border align-top"><td class="px-3 py-2 text-foreground">Prompts</td><td class="px-3 py-2 text-foreground">User-controlled</td><td class="px-3 py-2 text-foreground">Slash commands, menu options</td></tr></tbody></table></div></figure><p class="mt-4 leading-relaxed text-foreground">Servers and clients also negotiate capabilities. A server has to declare tool support before tools can be invoked, and a client has to declare sampling support before a server can request it. This lets each side add features at its own pace. The protocol can also run in the other direction: in Claude Code, an MCP server can act as a channel that pushes Telegram messages, Discord chats or webhook events into a session. A tool that Claude calls directly can only answer when Claude asks.</p><p class="mt-4 leading-relaxed text-foreground">Two transports carry the protocol, and the choice between them decides which clients can reach a server. With <strong class="font-semibold">stdio</strong>, the client launches the server as a subprocess and exchanges newline-delimited JSON-RPC messages over stdin and stdout. The server may log to stderr but must write nothing to stdout except valid MCP messages. Stdio is the transport behind the server that runs on a developer's laptop. With <!-- --><strong class="font-semibold">Streamable HTTP</strong>, the server is a remote endpoint. The client POSTs each JSON-RPC message to that endpoint, and the server answers with either one JSON object or an SSE stream. The client may also open a GET stream so the server can send messages without being asked.<!-- --></p><p class="mt-4 leading-relaxed text-foreground">A remote server takes on duties a subprocess never has. It must validate the <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">Origin</code> header on every incoming connection to block DNS rebinding. When it runs locally it should bind to 127.0.0.1 rather than 0.0.0.0, and it should authenticate every connection. tabular-nums font-normal text-muted-foreground">6<!-- -->.</span>When the system is better reached as another agent</h2><p class="mt-4 leading-relaxed text-foreground">Some systems need a whole agent rather than a tool. A tool or an MCP server gives Claude one function at a time, and the calling agent still does all the reasoning. A predefined agent brings its own model, system prompt, tools, MCP servers and skills. Handing work to it means handing over the judgement, together with the integrations that judgement needs.</p><p class="mt-4 leading-relaxed text-foreground">Here is a concrete case. A lead agent needs code review and test writing. Attaching every review tool and test runner to the lead fills its context and blurs its instructions. Routing the work to a reviewer agent and a test-writer agent, each with a focused prompt and its own tools, keeps each concern self-contained. The same reasoning applies when the system is an MCP server that only a specialist needs: attach it to the specialist agent, not to the agent that coordinates the work.</p><p class="mt-4 leading-relaxed text-foreground">Two properties of this option affect its design. Agents in a Managed Agents session share the same sandbox, filesystem and vault credentials, so a hand-off does not isolate permissions. It isolates context, because each agent runs in its own session thread with its own history. A subagent's thread also persists, so the lead can send follow-ups to a specialist that keeps its earlier work. Choose an agent over an MCP server when the conversation with the system may take several turns, not one request and one result.</p><aside class="my-6 rounded-lg border border-dashed border-border bg-muted/20 p-4"><p class="flex items-center gap-1.5 text-xs font-semibold uppercase tracking-wide text-muted-foreground"><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-circle-help h-3.5 w-3.5 shrink-0" aria-hidden="true"><circle cx="12" cy="12" r="10"></circle><path d="M9.09 9a3 3 0 0 1 5.83 1c0 2-3 3-3 3"></path><path d="M12 17h.01"></path></svg>Apply it to your own work</p><p class="mt-1.5 text-sm leading-relaxed text-foreground">Pick one system your team connects to Claude today.
