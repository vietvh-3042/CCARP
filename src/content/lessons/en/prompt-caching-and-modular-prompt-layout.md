data-lesson-section=""><span class="mr-2 tabular-nums font-normal text-muted-foreground">1<!-- -->.</span>What prompt caching reuses and what it costs</h2><p class="mt-4 leading-relaxed text-foreground">Many production prompts open with the same few thousand tokens every time: tool definitions, a long system prompt, a block of examples, a reference document. Prompt caching lets later requests skip reprocessing that shared opening. When a request arrives with caching enabled, the system checks whether the prompt prefix up to a cache breakpoint is already cached from a recent query. On a hit it uses the cached version, which cuts processing time and cost. On a miss it processes the full prompt and caches the prefix once the response begins. The workloads that gain most are prompts with many examples, large background context, repetitive tasks with consistent instructions, and long multi-turn conversations.</p><p class="mt-4 leading-relaxed text-foreground">A cache entry lives for <strong class="font-semibold">5 minutes</strong> by default, and every use refreshes it at no extra cost. A 1-hour TTL is available at 2x the base input price. The lifetime counts from the <strong class="font-semibold">start</strong> of the request that writes or reads the entry, not from the end of its response. Generation time therefore uses up the window: if a response takes 4 minutes to stream, a follow-up that reuses the same prefix has to start within about 1 minute of that response finishing. With a 5-minute TTL, a slow agent loop or a user who pauses for a while finds the cache gone.</p><p class="mt-4 leading-relaxed text-foreground">Caching changes the price of input tokens. Writing to the cache costs more than plain input, and reading from it costs a small fraction of plain input. Cache hits are 0.05x the base input price on Claude Opus 5.5 and Claude Sonnet 5.5, 0.025x on Claude Fable 5.1 and Claude Mythos 5.1, and 0.1x on every other model. Breakpoints themselves cost nothing. text-foreground">Caching can be turned on in two ways. <strong class="font-semibold">Automatic caching</strong> uses a single <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">cache_control</code> field at the top level of the request. The system places the breakpoint on the last cacheable block and moves it forward as the conversation grows, so you never edit markers by hand. On each turn, everything up to the previous request's end is read from cache, and only the new assistant reply and user message are written. <strong class="font-semibold">Explicit breakpoints</strong> put <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">cache_control</code> on individual content blocks. It also returns 400 if the last block already carries an explicit marker with a different TTL. If that marker has the same TTL, automatic caching does nothing extra.
