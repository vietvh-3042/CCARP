The first design question is whether you need it at all. A knowledge base under about 200,000 tokens, roughly 500 pages, can go into the prompt whole, and prompt caching keeps repeated requests fast and cheap. RAG is worth its extra moving parts once the corpus no longer fits in the context window.</p><p class="mt-4 leading-relaxed text-foreground">Most of a RAG pipeline's work happens at ingestion. The corpus is split into chunks, usually no more than a few hundred tokens each. An embedding model turns each chunk into a vector, and a vector database stores those vectors so they can be searched by semantic similarity. At query time, the closest chunks are added to the prompt sent to Claude.</p><p class="mt-4 leading-relaxed text-foreground">Chunk size, chunk boundary and chunk overlap are three settings you tune, and each one can change retrieval performance. Splitting on headings keeps each subsection's content together. A basic character splitter cuts wherever the character count runs out, whatever the text says at that point. Overlap belongs in the same list. Removing it to speed up indexing changes retrieval, so measure the effect like any other retrieval change.</p><p class="mt-4 leading-relaxed text-foreground">Every chunk size has the same cost: once split off, a chunk loses the document around it. Take a set of SEC filings and the chunk 'The company's revenue grew by 3% over the previous quarter.' It answers a question about ACME Corp's revenue growth in Q2 2023, but it names neither the company nor the quarter. A query about ACME in Q2 2023 has little in that chunk to match. Even if the chunk is retrieved, Claude can't tell which company it describes.</p><p class="mt-4 leading-relaxed text-foreground">There are two ways to put that context back. One is to write it into each chunk before indexing; this is contextual retrieval, covered below. The other is a contextualized chunk embedding model such as <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">voyage-context-4</code>. It produces chunk-level vectors that carry the whole document's context without you adding metadata by hand. Some embedding models have a fixed input token limit. If contextualized chunks retrieve worse than plain ones, the added text may be pushing them past that limit so they get truncated. The fix is a model with a larger context window. <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">voyage-law-2</code>, for example, accepts half the input of the general-purpose models.</p><p class="mt-4 leading-relaxed text-foreground">Embed documents and queries differently. Set <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">input_type="document"</code> when you embed chunks and <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">input_type="query"</code> when you embed the user's question. Don't omit the parameter or set it to <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">None</code>. Voyage prepends a different instruction to each kind of input: 'Represent the document for retrieval: ' for chunks and 'Represent the query for retrieving supporting documents: ' for questions. This gives better vectors for retrieval, which in turn improves retrieval quality.</p><p class="mt-4 leading-relaxed text-foreground">Voyage vectors are normalized to length 1. That makes cosine similarity equal to dot product, and dot product is quicker to compute. Euclidean distance gives the same ranking too, so the similarity metric you choose won't change which chunks come back.</p><p class="mt-4 leading-relaxed text-foreground">Two output settings make the index smaller without making retrieval more accurate. <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">output_dtype</code> quantizes each vector. With <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">int8</code> or <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">uint8</code>, storage, memory and cost drop by 4x; with <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">binary</code> or <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">ubinary</code>, they drop by 32x. The default, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">float</code>, keeps the highest precision and retrieval accuracy. <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">output_dimension</code> (for example 256 instead of the default 1024) returns shorter Matryoshka vectors, and vectors you've already stored can be cut down to their leading dimensions and normalized again. Use these settings when index size or cost is the problem. text-foreground">Contextual retrieval writes the missing document context back into each chunk before indexing. For each chunk, Claude receives the whole document and the chunk and returns a short context, usually 50 to 100 tokens, that places the chunk within the document. That context is prepended to the chunk. The ACME chunk becomes 'This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million.' followed by the original sentence.</p><figure class="my-6"><figcaption class="mb-1.5 flex items-baseline justify-between gap-3"><span class="text-xs text-muted-foreground">The contextualizer prompt Anthropic used with Claude 3 Haiku to generate per-chunk context</span><span class="shrink-0 rounded bg-muted px-1.5 py-0.5 font-mono text-[10px] uppercase tracking-wide text-muted-foreground">text</span></figcaption><pre class="overflow-x-auto rounded-lg border border-border bg-muted/50 p-4 text-[13px] leading-relaxed"><code class="font-mono text-foreground">&lt;document&gt;&#10;{{WHOLE_DOCUMENT}}&#10;&lt;/document&gt;&#10;Here is the chunk we want to situate within the whole document&#10;&lt;chunk&gt;&#10;{{CHUNK_CONTENT}}&#10;&lt;/chunk&gt;&#10;Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else.</code></pre></figure><p class="mt-4 leading-relaxed text-foreground">The same contextualized chunk goes into both indexes. Pipelines keep a lexical index next to the vector index because embeddings can miss exact strings, such as error code TS-999, that BM25 matches (<a class="text-primary underline underline-offset-2 hover:no-underline" href="/en/lessons/retrieval-strategy-selection-full-context-embeddings-bm25-and-hybrid-search/">Semantic embeddings vs BM25, and hybrid search</a>). Prepend the generated context before embedding the chunk; this is contextual embeddings. Prepend the same text before tokenizing the chunk for the BM25 index; this is contextual BM25. The original chunk text is still there, so BM25 still matches product codes and error strings exactly. It now also matches the company names, periods and file names that appeared only elsewhere in the document.</p><p class="mt-4 leading-relaxed text-foreground">Each index improves measurably. Across codebases, fiction, ArXiv papers and science papers, contextual embeddings alone cut the top-20 retrieval failure rate by 35%, from 5.7% to 3.7%. Adding contextual BM25 raised the cut to 49%, bringing the failure rate to 2.9%. Contextualizing helped with every embedding model tested, and Gemini and Voyage embeddings gained the most.</p><p class="mt-4 leading-relaxed text-foreground">The context has to be about the specific chunk. Attaching a generic document summary to every chunk gave very limited gains, and summary-based indexing performed poorly. The generic prompt above works well. A prompt tailored to your domain can work better, for example one that includes a glossary of terms defined only in other documents.</p><p class="mt-4 leading-relaxed text-foreground">Prompt caching keeps the cost down. Each chunk's request repeats the whole document, so put the document first and mark the end of it with <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">cache_control</code>. The first chunk writes the document to the cache, and the following chunks read it at a 90% discount. The cache lasts five minutes, so process each document's chunks one after another instead of mixing chunks from different documents. With 800-token chunks, 8k-token documents and 100 tokens of context per chunk, generating the context costs $1.02 per million document tokens. That cost is paid once, at ingestion, not on every query.
