Anthropic's incident log lists real cases: deleting remote git branches after misreading an instruction, uploading an engineer's GitHub auth token to a compute cluster, and attempting migrations against a production database. None of these came from hostile intent. In each case the model was overeager and <strong class="font-semibold">takes initiative beyond what the user would approve</strong>.</p><p class="mt-4 leading-relaxed text-foreground">Human-in-the-loop validation means putting a person between the agent and those actions. The design problem is placing the person well. If every action asks for approval, people stop reading the prompts: Claude Code users approve 93% of permission prompts. If nothing asks, nobody catches the deleted branch. A good design sends routine reads and edits through without a prompt and saves the person's attention for actions that are irreversible, touch shared infrastructure or send data outside the organisation.</p><p class="mt-4 leading-relaxed text-foreground">Claude offers three surfaces for this. Claude Code uses <strong class="font-semibold">permission modes</strong>. The Agent SDK uses a <strong class="font-semibold">canUseTool</strong> callback that your application answers. Managed Agents use <strong class="font-semibold">permission policies</strong> that pause a session until your client confirms. give different kinds of human-in-the-loop control, and they are easy to confuse. <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">plan</code> lets Claude investigate freely but keeps your source files untouched until a person signs off. Claude Code blocks edits until you approve a plan. <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">dontAsk</code> is for runs with no person present. It turns every would-be prompt into a denial, so a CI job never sits waiting on a question nobody will answer. Calls approved by <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">allowedTools</code> or allow rules still run. In the SDK, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">canUseTool</code> is never called in this mode. A headless run with <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">--dangerously-skip-permissions</code> behaves the same way: the few calls that would still prompt are denied instead.</p><p class="mt-4 leading-relaxed text-foreground">In <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">auto</code> mode a model-based classifier takes the human approver's place. Before shell commands and network requests run, it checks that they match what the user asked for. Approval fatigue is the reason it exists. It does not remove the person entirely.</p><p class="mt-4 leading-relaxed text-foreground">Some actions reach a person in every mode, including <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">auto</code> and <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">bypassPermissions</code>, which skips permission prompts except for the actions no mode auto-approves. That makes an ask rule a checkpoint that survives a mode change. What the person sends back matters too. On a prompt they can attach a comment. If they choose <strong class="font-semibold">Yes</strong>, Claude Code runs the action and then gives Claude the comment. If they choose <strong class="font-semibold">No</strong>, the comment goes to Claude as the reason for the denial and Claude keeps working. The SDK calls it in two situations. The first is when Claude wants a tool that no permission rule or mode has auto-approved. The second is when Claude calls <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">AskUserQuestion</code> to ask a clarifying question. The callback receives the tool name, the tool's input and a context object. You show those to a person, wait for their decision and return it. For Bash, the input carries <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">command</code>, <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">description</code> and <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">timeout</code>. For Write, it carries <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">file_path</code> and <code class="rounded bg-muted px-1 py-0.5 font-mono text-[0.9em] text-foreground [overflow-wrap:anywhere]">content</code>.
