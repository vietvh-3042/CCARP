class="mt-12"><h2 id="section-3" class="scroll-mt-20 text-xl font-semibold leading-snug text-foreground" data-lesson-section=""><span class="mr-2 tabular-nums font-normal text-muted-foreground">3<!-- -->.</span>Routing: split by input type, and match the model to the subtask</h2><p class="mt-4 leading-relaxed text-foreground"><strong class="font-semibold">Routing</strong> classifies an input first, then sends it to a follow-up step built for that category. That step can use its own prompt, its own tools or its own model. The reason to route is interference. If one prompt has to serve every kind of input, tuning it for one kind tends to make it worse for the others. A customer-service system might route general questions, refund requests and technical support into three separate processes, each with its own prompt and tools.</p><p class="mt-4 leading-relaxed text-foreground">Routing works when the categories really are distinct and <strong class="font-semibold">classification can be done accurately</strong>, whether by an LLM or by a traditional classifier. If inputs are often misclassified, every downstream specialist receives work it was not built for.</p><p class="mt-4 leading-relaxed text-foreground">Routing is also the place to choose a model for each subtask. Model classes differ mainly in how hard a problem they can reliably handle and what that capability costs in price and speed. Easy, common requests go to a small, cheap model. Hard or unusual ones go to a more capable model. Take a support pipeline with two subtasks: classifying a large stream of tickets, and drafting detailed remediation plans for the few that need engineering. Classification goes to Haiku.
